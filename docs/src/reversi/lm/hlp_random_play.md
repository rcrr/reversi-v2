# reversi/lm/hlp_random_play.py
The SU_ANALYSIS frequency data plane: the streaming per-sub-variable (code -> count) marginal + joint frequency
accumulators over the corpus. The corpus is generated by the wave engine (hlp_wave.run_wave, the wave engine) and fed
chunk-by-chunk; this module accumulates the frequencies, it does not generate the corpus. Also carries the `ec_of` /
`initial_position` utilities (the ec formula + the standard start, the shared board helpers).

## API
- `ec_of(p)` — the ec formula: 64 - the occupied squares (the moves remaining; the same expression
  board.position_final_value uses inline). PINNED: EXACTLY the DB's `empty_count` — the regab extraction filters
  `empty_count = ec` (regab.py, the "mele con mele" window constraint); `empty_count` = the empty squares = 64 -
  popcount(mover | opponent). The corpus is arrested in the SAME window as the DB extraction.
- `initial_position()` — the standard start (the official Othello setup: the mover (black, the starting player) E4+D5,
  the opponent (white) D4+E5 — the 2x2 center, both sides 4 legal moves, ec = 60; board.initial_game_position is the
  canonical source).
- `MarginalAccumulator(fset, blocks)` — the streaming marginal frequency accumulator: per sub-variable (the (feature,
  instance) column) the code -> count. The analysis unit is ONE design-index column (the design-matrix unit the weights
  live on) — each pattern instance is its own categorical variable (the code a single uint32 in [0, n_conf), no packing
  / no overflow: the 2X5COR^8 structured-key concern is the feature-level / the joint statistics, not the per-column
  marginal). `.add(mover, opp)` feeds a corpus chunk (the wave boundary harvest); `.result()` returns per sub-variable
  (name, instance, n_conf, codes, counts) — the observed (non-zero support), len(codes) = K_obs, never-observed =
  n_conf - K_obs. The split: n_conf <= _DENSE_THRESHOLD (1e6; the A2050 max is 59049) -> the DENSE bincount, else the
  UNIQUE-MERGE dict. POOLED over all fed positions (the single-ec corpus — no per-ec split).
  - `JointAccumulator(fset, blocks, su_pairs)` — the streaming joint frequency accumulator: per REQUESTED su pair (F_i,
    F_j) and per (instance_i, instance_j) in the pair, the (code_i, code_j) -> count — the instance×instance level (P6's
    matrix). The joint is SPARSE (the code_i x code_j space is too large for the dense — the unique-merge split). The
    key is the packed u64 (code_i * n_conf_j + code_j) — safe for the A2050 scale (the max is 59049^2 << 2^64). The
    same-feature pair (F, F) is allowed: the accumulator BUILDS the diagonal (inst_i == inst_j) too — the SU report
    omits it downstream (the SU = 1 lock); the off-diagonal (the D8 orientations of the same mask) is the anisotropy
    measure. `.result()` returns per pair (name_i, name_j, { (inst_i, inst_j): (codes_i, codes_j, counts) }).

## Architecture
- The streaming accumulator: the corpus is fed chunk-by-chunk (the wave boundary harvest, the BufferSink); the
  accumulator pools over all fed positions (the single-ec corpus — no per-ec split). The `.add(mover, opp)` is the chunk
  entry; the `.result()` is the harvest.
- The ec pin: the `ec_of` is the DB's `empty_count` (the "mele con mele" window) — the corpus is arrested in the SAME
  window as the DB extraction.

## Verified invariants
Pinned by `test_hlp_random_play.py` (5 classes / 10 tests, no DB): `TestEcPin` (the hand-counted ec), the two
accumulators (the LMC oracle + the R2 cross-check, the chunk-merge invariance, the cross-feature + the diagonal joints),
the PRNG integration (the corpus reproducibility + the small end-to-end marginals).
- The ec pin: ec_of = 64 - the occupied squares, hand-counted over the initial position (4 stones, ec 60) + a
  hand-crafted 24-stone position (ec 40) + the full board (ec 0). This IS the DB's `empty_count` (the regab
  `empty_count = ec` filter) — the "mele con mele" window.
- The marginal accumulator (the toy corpus, a 300-game wave at ec 20, the toy FeatureSet = the intercept + the LMC + the
  R2): the LMC (single-instance, the dense bincount) hand-counted against the INDEPENDENT oracle position_legal_moves
  (the legal-move count per position — NOT compute_indexes); the R2 inst0 (multi-instance feature, one column)
  cross-checked against an independent per-position dict count via compute_indexes; the CHUNK-MERGE invariance (one
  chunk == two half-chunks, the dense + the merge are chunk-invariant). Every sub-variable's count sum == N, every K_obs
  <= n_conf.
  - The joint accumulator (the same toy corpus, a 200-game wave at ec 20): the (LMC, R2) cross-feature pair (the 4
    instance-pairs (0, j)) + the (R2, R2) same-feature pair (the 16 instance-pairs (4 x 4)), each joint (code_i,
    code_j) -> count cross-checked against the INDEPENDENT per-position oracle (the manual dict via compute_indexes);
    the SAME-FEATURE DIAGONAL (ii, ii) has ZERO off-diagonal entries (the variable with itself, code_i == code_j always
    — the SU = 1 lock); the CHUNK-MERGE invariance (one chunk == two half-chunks, the marginals and the joints alike).
    Every joint's count sum == N.

## Open issues
- The mover-convention alignment with the DB extraction: the mover is FIXED by the official Othello rules (black, E4+D5,
  the starting player — the official Othello setup); the setup is NOT mover-symmetric — the mover/opponent roles are
  fixed by that start, not interchangeable labels — so the corpus convention must match the DB extraction.

## Conventions
- The house GNU header + the provenance docstring (the doc sections, the design rationale).
- The naming convention: the square names uppercase (D4, E5 — board.py move_from_str), A1 = top-left = bit 0.
- The module docstring carries the design rationale (the streaming accumulator, the ec pin).

## Integration
- Consumes `board.py` (the Position, the legal moves); the PRNG (tools/prng.py) is driven by the wave engine (hlp_wave),
  not here.
- Consumer: the SU_ANALYSIS level (the worker wrk_su_analysis.py) — the accumulators are the phase-1 (corpus ->
  frequency tables) data plane; the corpus is the wave (hlp_wave.run_wave) fed chunk-by-chunk.
- Not a pipeline level itself: the lm data module of the SU_ANALYSIS level (like hlp_validate / hlp_plot).
